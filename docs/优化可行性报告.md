## 二、优化项(按优先级)

### 🔴 P0-1 推送可靠性兜底(今日事故的直接解药)
- **问题**:盘中 monitor 可能整个交易时段 0 次运行;15:35 日报可能不触发。今天的 9 条 S/A 信号就是因此没送到。
- **方案(推荐组合)**:
  - **A. 本机 cron 当"闹钟"**:VM 上 crontab 交易时段每 5 分钟 `gh workflow run monitor.yml` + 15:35 `gh workflow run auto-report.yml`。GitHub 调度拥堵时,本地定时器强制触发一次,用 `workflow_dispatch` 通道(该通道实测 18 秒内启动,比 schedule 可靠得多)。gh CLI 已认证、api.github.com 直连可达,**不需要开代理**。
  - **B. 补发自愈**:auto-report.yml 的 schedule 时间后加一个 `workflow_dispatch` 触发器 + 手动兜底脚本(已有 `gh workflow run` 操作经验)。
  - **C. 全迁本机**(最可靠但依赖开机):monitor + 推送全部本机跑,回到 8/17 前的模式。
- **工作量**:A+B 约 1 小时;C 约 2 小时。**风险:低**。
- **建议**:做 A+B。5 分钟级推送可靠性从"听天由命"提升到"本地补刀 + dispatch 通道"。

### 🔴 P0-2 持仓隐私脱敏(已第二次提醒)
- **问题**:公开仓库 `data/trades.json` 含真实成本/股数/已实现盈亏,任何人可看。
- **方案(按成本排序)**:
  - 最简:前端不再直读 trades.json,改为生成脱敏版 `trades_public.json`(去掉成本,只留代码/股数/方向/金额级数据),完整版只进邮件;
  - 中等:交易视图改为"本地输入 + 邮件自查",线上只显示汇总卡片;
  - 彻底:迁 Cloudflare Pages(私有源/访问控制),但国内访问性一般,且需同步链路。
- **工作量**:最简 1-2 小时;**风险:中**(改动交易页)。**建议:先做最简脱敏**。

### 🟡 P1-3 盘后信号补推(今天的信号不能白攒)
- **问题**:收盘后那次 monitor run 检测到 9 条 S/A,但 `is_trading_time` 门控拦下微信推送,攒进日报;日报又没发 → 信号丢失。
- **方案**:monitor 收盘后的 run 若检测到当日未推送的 S/A 信号,直接微信补推(force 模式放行)+ 日报生成时把攒批信号并入。需要给 digest/推送加当日去重(避免重复轰炸)。
- **工作量**:0.5-1 小时;**风险:低**。

### 🟡 P1-4 断板低吸回测正式化(Phase 3 待办)
- **现状**:东财涨停池接口历史只保留 15 个交易日,长周期回测缺数据;本地日K检测法样本仅 18 个(胜率 66.7%,仅方向参考)。
- **方案**:①每日落盘涨停池快照(monitor 已拉)→ 攒 2-3 个月数据;②回测切换本地 300 只池日K检测连板/断板(已有 verify_dragon.py 骨架);③样本≥100 后再下结论。
- **工作量**:积累任务 30 分钟 + 回测脚本半天;**风险:数据积累是硬约束,急不得**。

### 🟡 P1-5 AI 报告闭环(打脸复盘)
- **现状**:AI 报告每日 1 封,~1 分/天,只润色规则结论。
- **方案**:报告里加入"昨日建议 vs 今日实际"对照(自动判定打脸/应验),周复盘汇总准确率。让决策闭环真正闭环。
- **工作量**:1-2 小时;**风险:低**。

## 三、风险与依赖

1. **Actions 调度不可控是结构性约束**——免费 cron 是 best-effort,任何方案都要承认这一点;本机兜底依赖 VM 开机 + 网络(用户晚上常在,可接受)。
2. **公开仓库隐私是硬伤**——脱敏只是缓解,彻底解决需私有化部署或访问控制。
3. 断板低吸等数据驱动结论**必须攒够样本**,不要用 18 个样本做决策。
